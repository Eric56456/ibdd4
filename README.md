## 1. Цель и задачи работы

**Цель:** Получение навыков использования серверных языков программирования, фреймворков по работе с БД, ORM-систем и реализация прикладного уровня с многопользовательским доступом к базе данных `ConcertHub`.

**Выполненные задачи:**
1. Разработан пользовательский веб-интерфейс на базе **Python**, **Flask** и **SQLAlchemy 2.0 ORM** для отображения, добавления и удаления данных из БД.
2. Реализован многопользовательский доступ с использованием ролей и учетных записей СУБД PostgreSQL, настроенных в ЛР №1–3 (`ivan_customer`, `petrov_staff`, `admin_user`, `postgres`).
3. Реализовано динамическое формирование списка таблиц и представлений, доступных каждому типу пользователей на основе привилегий их ролей в БД.
4. Разработаны и внедрены в интерфейс сложные аналитические SQL-запросы с функцией `GROUP BY`, объединяющие более 2 сущностей (до 5 сущностей), с интерактивной сортировкой и фильтрацией для каждой категории пользователей.
5. Интегрирована система безопасности: аудит изменений через триггерную функцию `public.logging()` в `audit.main_log` и симметричное шифрование конфиденциальных токенов `pgcrypto` (`pgp_sym_encrypt`).

## 3. Ролевая модель доступа и права пользователей

В приложении используется прямое подключение к PostgreSQL от имени индивидуальных пользователей, созданных в ЛР №3:

| Пользователь в БД | Пароль | Групповая роль | Доступные таблицы и представления | Права CRUD |
|---|---|---|---|---|
| `ivan_customer` | `customer` | `customer_group_role` | `view_customer_afisha`, `view_customer_my_tickets`, `concert` | Только SELECT |
| `petrov_staff` | `staff` | `staff_group_role` | Все таблицы `public` (`concert`, `ticket`, `venue`, `hall_sector`, `artist`, `promoter`, `customer`, `ticket_order`), представления продаж и гейт-контроля | SELECT, INSERT, UPDATE, DELETE (на таблицы мероприятий) |
| `admin_user` | `admin` | `admin_group_role` | Все таблицы и представления в `public`, плюс схема `audit` (`audit.main_log`, `audit.secret_data`) | Полный доступ (ALL PRIVILEGES) |
| `postgres` | `postgres` | `superuser` | Все объекты СУБД | Полный доступ суперпользователя |

Если пользователь пытается запросить таблицу, на которую у его роли нет прав (например, `ivan_customer` запрашивает `artist` или `audit.main_log`), PostgreSQL возбуждает исключение `psycopg2.errors.InsufficientPrivilege`, которое перехватывается веб-приложением и наглядно выводится пользователю с кодом HTTP 403.

## 4. Сложные аналитические SQL-запросы с GROUP BY (п. 4 ТЗ)

### 4.1. Запрос для роли Зрителя (`Customer`)
- **Сущности (4 шт.):** `concert`, `artist`, `venue`, `ticket`.
- **Группировка:** по `concert_id`, `program_name`, `artist`, `venue_name`, `city`.
- **Агрегатные функции:** `COUNT(t.ticket_id)` доступных билетов, `MIN(price)`, `MAX(price)`, `AVG(price)`.
- **Фильтрация и сортировка:** фильтрация по городу, музыкальному жанру, максимальной цене; сортировка по дате, цене, названию.

### 4.2. Запрос для роли Организатора (`Staff`)
- **Сущности (5 шт.):** `concert`, `promoter`, `artist`, `venue`, `ticket`.
- **Группировка:** по `promoter_id`, `company_name`, `concert_id`, `program_name`, `artist`, `venue_name`, `total_capacity`.
- **Агрегатные функции:** `COUNT` проданных билетов, процент заполняемости зала `(tickets_sold / capacity * 100)`, суммарная выручка `SUM(price)`, средний чек `AVG(price)`.
- **Фильтрация и сортировка:** фильтрация по организатору, минимальной выручке; сортировка по выручке, заполняемости, дате.

### 4.3. Запрос для роли Администратора (`Admin`)
- **Сущности (4 шт.):** `artist`, `concert`, `venue`, `ticket`.
- **Группировка:** по `artist_id`, `stage_name`, `music_genre`.
- **Агрегатные функции:** число концертов `COUNT(DISTINCT concert_id)`, охват городов `COUNT(DISTINCT city)`, всего проданных билетов `COUNT(ticket_id)`, валовые сборы `SUM(price)`, средний доход за концерт.
- **Фильтрация и сортировка:** фильтрация по жанру, порогу проданных билетов; сортировка по сборам, числу концертов.
- **Дополнительно:** аналитика по журналу аудита `audit.main_log`, сгруппированная по типам операций (`I`, `U`, `D`) и операторам `user_operator`.

## 5. Быстрый запуск

### Вариант 1: Через Docker Compose (рекомендуется)
В корне проекта выполните:
```bash
docker compose up --build
```
Сервисы поднимутся автоматически:
- **Веб-интерфейс ConcertHub:** http://localhost:5000
- **PostgreSQL:** localhost:5432

### Вариант 2: Локальный запуск
1. Установите зависимости:
```bash
pip install -r requirements.txt
```
2. Примените миграции (при запущенном локальном PostgreSQL):
```bash
python src/migrations/runner.py
```
3. Запустите веб-приложение:
```bash
python src/main.py
```
Приложение будет доступно по адресу http://localhost:5000.
